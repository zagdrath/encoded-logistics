Jobs, scheduling and triggers

Interactive and batch jobs and their hosts, job logs, schedule entries, trigger events, message queues, spooled output, printing and system values.

All ELCL work runs in jobs. They are script jobs, separate from the network's crafting jobs (which WRKCRFJOB shows; see Crafting jobs). This page covers how jobs run and where, how to run them on a timer or when something happens, and where their messages and printed output go.

Jobs#

There are two kinds of job.

  • Interactive job. One for each open Terminal OS session (a Terminal Desk or an Integrated Midrange System's console), started by the session's first request. It is named QINTER, has type INT, runs on the desk's device name (ELDESK01), has priority 5 and always logs its commands. The commands you type run in it, and so does a program you start there with CALL: one at a time, elcl.interactiveBudget (default 200) instructions a tick. It ends when the terminal closes (ELC0307 in its log), ending any program it is running, and its log joins the kept logs of ended jobs. Interactive jobs last only as long as their session and aren't saved.
  • Batch job. Submitted with SBMJOB CMD(command) JOB(name) HOST(*ANY|host) LOG(*NO|*YES) (SBMJOB), by a schedule entry or by a trigger. It runs on a job host, elcl.batchBudget (default 100) instructions a tick, as the user who submitted it, with that player's Firewall permissions, whether they are online or not. Its command can be any command that works in batch; usually it is CALL PGM(...). SBMJOB answers ELC0304 and the job waits on the job queue (*JOBQ) until a host has room. With no JOB() the job is named QDFTJOBD.

Job hosts#

Batch jobs need a job host on the network. Each tick, queued jobs go to an online host with a free slot (any host for HOST(*ANY), else the one named), in priority order (1 first, 5 unless changed with CHGJOB JOBPTY()) and then oldest first, as long as fewer than QMAXJOB batch jobs are running on the system (see system values). A system with no job host at all refuses the job at once with ELC0301, and so does a HOST() it doesn't have.

A host counts only while it is online: a Compute Server while it is powered in its rack, a Midrange System while it is running (not during its IPL). See the Midrange line for the Midrange Systems.

When a host goes down. A running batch job's state is saved with the system, but no host carries a job on after it stops: when a job's host goes offline (unloaded, removed, out of power, or a Midrange System's IPL) or the server restarts, the job ends with ELC0310, which is logged and sent to the job's user. Jobs still on the job queue, and held jobs that hadn't started, wait through a restart and start once a host has room. For work that must survive a restart, use a schedule entry or a trigger: they submit a new job each time.

Job IDs and statuses#

  • Job IDs are nnnnnn/USER/JOBNAME, for example 000123/ZAGDRATH/RESTOCK. Commands take the number, the full ID, or the job name alone if only one job that hasn't ended has it (ELC0302 otherwise). Numbers start at 000001 on each system, are shared by interactive and batch jobs, are saved, and wrap round after 999999.
  • Statuses: *JOBQ (waiting for a host), *ACTIVE, *WAIT (in a DLYJOB or DLYTICK, a tape recall or a craft it waits for), *HELD, and *ENDED (an ended job whose log is kept).
  • Holding, releasing, ending. HLDJOB holds a queued job (it won't start) or pauses a running one where it is; RLSJOB lets it go on (back to *JOBQ if it hadn't started). ENDJOB takes a queued job off the queue or stops a running program: OPTION(*CNTRLD) lets the command it is running finish, *IMMED stops it at once. The batch job then ends with ELC0303 in its log and in its user's messages.
  • Other users' jobs. You can hold, release, change and end your own jobs. Doing it to another user's job takes *SECOFR (the Firewall's owner or a server operator), or a network with no Firewall or at SECLVL 10; otherwise it is ELC0401 naming *JOBCTL.
  • Unmonitored errors. A program ended by an escape message it didn't catch puts that message in the job log and in the job user's message queue, then the job ends.
  • Budget. Work with Active Jobs shows how much of its per-tick budget each job used on the last tick; see the runtime model.

Commands on jobs: WRKACTJOB, WRKJOB, DSPJOBLOG, CHGJOB (priority 1 to 9, command logging), HLDJOB, RLSJOB, ENDJOB, SBMJOB and RTVJOBA (a program's own job: its user, name, type and host).

SBMJOB CMD(CALL PGM(ELSYS/NOCWALL)) JOB(NOCWALL)    /* ELC0304, then *ACTIVE on CMPSRV01 */
SBMJOB CMD(CALL PGM(ZAGLIB/RESTOCK) PARM('IRON_INGOT' 500)) JOB(RESTOCK) LOG(*YES)
CHGJOB JOB(RESTOCK) JOBPTY(1)                      /* to the front of the queue          */
ENDJOB JOB(NOCWALL)                                /* ELC0311, then ELC0303 in its log    */

Job logs#

Every job keeps a log of the commands it ran (when it logs commands: always for the interactive job, and for a batch job with LOG(*YES) on SBMJOB or CHGJOB LOG(*YES)) and every message it got, with its ID, severity, sender and time. A batch job's log starts with ELC0304 and ends with how it ended: ELC0307, the escape message that ended it, ELC0303 or ELC0310.

View a log with DSPJOBLOG or WRKJOB option 10, or print it with PRTRPT RPT(*JOBLOG) from inside the job. When a job ends its log is kept with the system's ended jobs: the last LOGRTN of them, saved with the system. Name an ended job by its number or full ID to see its log.

Job schedule entries#

ADDJOBSCDE JOB(name) CMD(command) FRQ(*ONCE|*DAILY|*INTERVAL) TIME(HHMM) INTERVAL(seconds) adds an entry that submits CMD as a batch job, named after the entry, when it is due.

  • *ONCE (the default): the next time the game clock reaches TIME (HHMM or HHMMSS; the game day starts at 06:00). *CURRENT, the default TIME, means now. The entry is removed once it has run.
  • *DAILY: every day at TIME on the game clock. If its network was unloaded through one or more of its times, it runs once when the network is loaded again, not once for each day missed.
  • *INTERVAL: every INTERVAL real seconds (1 to 604,800; needed with FRQ(*INTERVAL)), the first run that long after the entry is added. It is real time, so it keeps its pace whatever the game clock or the server's tick rate does.

How entries behave:

  • They fire only while their network is loaded, whether or not anyone is signed on.
  • The job runs as the user who added the entry, with their Firewall permissions. If it can't be submitted (no job host: ELC0301), the message goes to that user's message queue as "Schedule entry NAME: ...".
  • Work with Job Schedule Entries (WRKJOBSCDE) shows each entry's next run on the game clock (an *INTERVAL entry's as near as real seconds go). Option 10 submits it now without changing its next run.
  • HLDJOBSCDE holds an entry (status *HLD; it doesn't fire) and RLSJOBSCDE releases it (*SCD); both answer with no message. RMVJOBSCDE removes one. An entry name that is taken is ELC0305, and one that doesn't exist is ELC0302.
  • Entries are saved with the system.
ADDJOBSCDE JOB(ARCHIVE) CMD(CALL PGM(ELSYS/ARCHIVE) PARM('*_ORE')) FRQ(*DAILY) TIME(0200)
ADDJOBSCDE JOB(RESTOCK) CMD(CALL PGM(ZAGLIB/RESTOCK) PARM('IRON_INGOT' 500)) +
           FRQ(*INTERVAL) INTERVAL(300)
ADDJOBSCDE JOB(WAKEUP) CMD(SNDMSG MSG('Morning') TOUSR(*ALL)) TIME(0600)

Trigger events#

ADDTRGEVT TRG(name) EVENT(event) PGM(lib/program) ITEM() DEV() VALUE() TYPE() runs a program as a batch job, named after the trigger, whenever something happens on the network. It runs as the user who added the trigger, as CALL PGM(program) PARM('event' 'data'), so the program must take exactly two parameters:

PGM PARM(&EVENT &DATA)
  DCL VAR(&EVENT) TYPE(*CHAR) LEN(12)    /* the event's name, *SUPFAILOVER the longest */
  DCL VAR(&DATA)  TYPE(*CHAR) LEN(256)   /* what happened: see the table               */
  SNDMSG MSG(%TRIM(&EVENT) *BCAT %TRIM(&DATA)) TOUSR(*SYSOPR)
ENDPGM

The event name arrives whole; a variable shorter than the name cuts it (a LEN(10) &EVENT gets *DEVOFFLIN for *DEVOFFLINE), so declare &EVENT LEN(12). ITEM(), DEV() and VALUE() narrow what fires the trigger, as the table says; *ANY (the default) takes any. VALUE() takes text, so quote a side: VALUE('*NORTH'). TYPE(*FLUID) or TYPE(*PRES) makes *ITMBELOW and *ITMABOVE watch a fluid or a gas.

How triggers behave:

  • Edge-triggered. A trigger fires once each time its condition becomes true, not for as long as it holds. Item counts, storage use, UPS power and device statuses are looked at every half second. The first look after a trigger is added (or after a restart) only records what holds, so a condition that is already true doesn't fire. The other events arrive as they happen: ended and stalled crafts, redstone changes, touches, Router, chassis and optical events, and Arcforge machine events (the machine ones only while the machine's Small Wireless Bridge is online on the network).
  • Debounced. At least one second (real time) passes between two firings of the same trigger. A crossing during that second fires when it's over, if it still holds; events during it fire once then, with the last &DATA.
  • Needs a job host. Each firing is a batch job. With no host, ELC0301 goes to the trigger's user's message queue as "Trigger NAME: ...".
  • Only while the network is loaded. Held triggers (HLDTRGEVT, status *HELD) don't fire, and a firing waiting out its debounce when the trigger is held is dropped; RLSTRGEVT makes it *ACTIVE again. Both answer with no message. RMVTRGEVT removes one. Removing, holding or releasing a trigger that doesn't exist is ELC0103, and a name that is taken is ELC0306.
  • Triggers are saved with the system. Device statuses aren't: a device that changed while the server was down doesn't fire.

Message queues#

Each user has a message queue, shown newest first by DSPMSG (Main Menu option 7). While it holds unread messages, MW shows at the end of the message line on every screen.

SNDMSG MSG('text') TOUSR(...) puts a message in a queue:

  • *REQUESTER (the default): your own queue.
  • a user's name: that user's queue.
  • *SYSOPR: the system operator's queue, QSYSOPR. Its chat notice goes to the network's owner (the Firewall's owner).
  • *ALL: every queue that already exists on the system, plus QSYSOPR.

DSPMSG shows your own queue. DSPMSG USR(*SYSOPR) shows QSYSOPR, and DSPMSG USR(name) another user's queue, to a *SECOFR (or anyone, on a network with no Firewall or at SECLVL 10); anyone else gets ELC0401.

  • Online recipients get a chat notice that a message is waiting (elcl.messageChatNotice (default true)).
  • The system puts messages in queues too: a job's unmonitored escape message goes to its user's queue (sent by the program); a batch job ended by ENDJOB or a lost host (ELC0303, ELC0310) and a schedule entry or trigger that couldn't submit its job are sent by QSYS.
  • Queues are saved with the system and keep at most elcl.messageCap (default 500) messages each; past that the oldest go. No message needs a reply.
  • SNDMSG's TOTRM() is accepted and ignored.

Spooled output#

Spooled files are printed output kept on the system, listed by Work with Output (WRKSPLF, Main Menu option 8) and shown with Display Spooled File (option 5). You see your own files. Each belongs to a job and has a name, a page count (60 lines a page), a status (*RDY when made) and the time it was made. They are saved with the system, at most elcl.spooledFileCap (default 200) on each system; past that the oldest go.

Printing#

Printing on paper goes to a printer on the network, the Line Printer: Work with Output option 6 (to the first online printer) and PRTRPT.

PRTRPT RPT()Prints
*INVEvery item in the network with its hot and cold counts, sorted by ID, then the total.
*DEVEvery named device with its type, status, lanes and location.
*JOBLOGThe log of the job it runs in.
*SPLFOne of the job's spooled files: SPLF(name), or *LAST (the default) for its newest; ELC0103 if it has none.
  • Each report starts with a heading line (its title, the date and SYSNAME).
  • DEV(*DFT) is the first online printer; or name one (PRT01).
  • Printed: ELC1307. No printer: ELC1301 (naming PRT01 for *DFT); offline: ELC1302; out of paper: ELC1306.

The Midrange line, Display Panels and Arcforge machines#

These devices have their own pages; here is what ELCL does with them.

  • The Midrange line. A Midrange System or Integrated Midrange System is a job host (above) and a diskette drive for SAVLIB and RSTLIB; its batch jobs end when it does an IPL. Its control panel's command line, and the Disk and Tape Drives' screens, run commands as a Terminal Desk's does. See the Midrange line.
  • Display Panels. A Display Panel screen is a device named DSP01, DSP02... SNDDSPTXT writes its text lines, CHGDSPRGN, SNDDSPWDG, SNDDSPGPH and SNDDSPIMG set up a dashboard, CLRDSP clears it and RTVDSPSIZ gives its size. A screen has two modes, Text and Dashboard; one that a program sets up regions or widgets on becomes a Dashboard. Touching a screen fires *DSPTOUCH. These commands need no Firewall permission. See Display Panels and the DSPDASH example in Worked examples.
  • Arcforge machines. With Arcforge installed, a Small Wireless Bridge puts a machine on the network as a device (ARCCRU01, by type). WRKMCH, RTVMCHSTS, RTVMCHSTAT and RTVMCHLST read them (the Firewall's view permission); CHGMCHSTS and CHGMCHCFG switch them and change their settings (build permission). The *MCH... trigger events report them. Without Arcforge the machine commands answer ELC1318. See Arcforge.

System values#

System values are settings for the whole system (the network). Work with them on WRKSYSVAL, or with RTVSYSVAL and CHGSYSVAL. Changing one takes *SECOFR (the Firewall's owner or a server operator), or a network with no Firewall (ELC0401 otherwise); a value outside its allowed ones is ELC0103, and a change answers ELC0222. Values are folded to upper case and saved with the system (only those changed from their defaults).
