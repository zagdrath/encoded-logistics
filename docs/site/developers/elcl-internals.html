Terminal OS and ELCL internals

Contributor notes on the Terminal OS and ELCL code - the package layout, how a command line runs, how to add a command, the services behind the screens, and the tests.

On this page

  2. How a command line runs

Notes for people working on the mod's own Terminal OS and ELCL code. Adding a command from another mod is on Extension points; the language itself is on The ELCL language. The design documents the code started from are in the repository's docs/elcl/ folder; where they and the code differ, the code wins, and this site follows the code.

How a command line runs#

  1. CrtTerminal.runCommand (client): clear is handled here; ScreenCommands.open opens a screen for a screen command; anything else goes to the server as a COMMAND request.
  2. TerminalDeskMenu starts the session's interactive job if it needs one and calls TerminalService.handle.
  3. The terminal package's command-line class hands the line to ElclCommandLine.run. (The screens' own requests, such as withdrawing an item, go to TerminalService, not the command line.)
  4. CommandRunner.run: Parser.parseCommand; an unknown command is ELC0101; a command that can't run on a command line is ELC0106; then Compiler.checkCommand; the Firewall permission through Authority (ELC0401; CONFIGURE means BUILD); no executor is ELC0107; then the executor, with an Invocation whose values are worked out from the literals typed. CALL's executor (InteractiveCalls) starts a VM in the interactive job and returns at once (ELC0108); JobManager runs it on the following ticks and sends its messages to the terminal when it ends.
  5. ElclCommandLine logs the command and its messages in the interactive job and formats the output; the response carries the unread message count for the MW indicator.

Inside a program the VM does the same for each command (Vm.registered): the context check (ELC0105 / ELC0106), the authority through the run's VmHost (a batch job uses its submitter's permissions; a PLC its loader's), then the executor with an Invocation over the frame's variables. An executor that has to wait calls call.await(Wait) when call.canWait(); the VM parks the job and runs the command again (with call.resumed() set) once Waits says the wait is done.

The OS screens fetch their data with SCREEN requests that ScreenQueries answers (libraries, members, source, locks, saving a member in pieces, jobs, job logs, call stacks, schedules, triggers, messages, spooled files, system values, sign-on, the prompter's value lists, and the database screens through FileQueries). These need the Firewall's VIEW permission, and until a session has signed on (where it must), only info and signon are answered.

How to add a command#

Register the schema once. The built-in ones go in BuiltinCommands.register(), which CommandRegistry runs when it loads:

CommandRegistry.register(CommandDefinition.of("RTVFOO", "Retrieve Foo")
        .auth(CommandDefinition.Auth.VIEW)         // Firewall permission (default NONE)
        .positional(1)                             // the first N parameters may omit their keywords
        .p(ParamDef.of("DEV", "Device", ParamDef.Kind.DEVICE).req())
        .p(ParamDef.of("MODE", "Mode", ParamDef.Kind.SPECIAL).sv("*FAST", "*SLOW").dft("*FAST"))
        .p(ParamDef.of("RTNVAL", "Return value", ParamDef.Kind.VARIABLE).returns(ParamDef.VarType.INT))
        .build());

The context defaults to BOTH; use .context(CommandDefinition.Context.INTERACTIVE) (or BATCH, PROGRAM) as needed. Other parameter builder calls: .list(n), .range(min, max), .len(n) (the prompter's field), .values(ValueList.X) (the F4 list). Registering a name twice throws.

Bind the executor. The built-ins are bound in ElclSetup.init, through each area's bind() (OsCommands.bind, RedstoneCommands.bind, ...):

CommandRegistry.bind("RTVFOO", call -> {
    ElclContext context = call.context(ElclContext.class);   // server, network, user, allowed()
    String dev = call.text("DEV");                           // names and special values upper-cased
    if (notFound) throw new ElclException("ELC1301", dev);   // an escape message
    call.returns("RTNVAL", 42);                              // a RTN* value
    call.send(ElclMessage.of("ELC0222", "FOO"));             // an informational or completion message
});

call.integer() raises ELC0003 and ELC0004 itself; call.given() tells a given value from a default; call.list() returns every value of a list parameter; call.interactive() says whether it runs at a terminal; call.canWait(), call.await() and call.resumed() make it asynchronous in a program.

That's all for the language side: the parser, the compiler's checks, the F4 prompter, F1 help, the command line and the VM all read the definition, and the same executor runs on the command line, in interactive programs and in batch jobs. Then:

  • Messages: new ones go in ElclMessages (and docs/elcl/MESSAGES.md). A completion message should be added to ElclCommandLine's COMPLETION set so it shows bright.
  • Parameters required only together are checked in the switch in the compiler's statement check.
  • On a PLC without a network only the commands in Compiler's PLC-local set run; add a command there only if it needs nothing from a network.
  • A device scripts talk to: give it a name (NamedDevice, with its type code; ElclDevices gives and keeps the names), and if it is a printer, diskette drive, display or job host, implement the interface in elcl.device or elcl.job and register a source at setup.
  • A command that opens a screen: add it to ScreenCommands, write a CrtPanel (or OsListPanel) subclass, add the crt.encodedlogistics.* lang keys (title, F-keys, help.<id> and help.<id>.<field>), and a layout under src/test/resources/layouts/ for LayoutTest.
  • The documentation: every command needs a category in docs/site-src/notes/command-categories.json (the docs build fails otherwise), and may have extra text in docs/site-src/notes/commands/<NAME>.md. Its reference page is generated from the schema; see Building this site.

Services#

ElclServices holds one implementation of each service the screens and commands use. All of them keep their data in the system's saved data (elcl.store), and each can be replaced for tests:

ElclServices.setLibraries(LibraryService)   // StoredLibraryService
ElclServices.setFiles(FileService)          // StoredFileService
ElclServices.setJobs(JobService)            // elcl.job.StoredJobService
ElclServices.setMessages(MessageService)    // StoredMessageService
ElclServices.setSpool(SpoolService)         // StoredSpoolService
ElclServices.setSysvals(SysvalService)      // StoredSysvalService
ElclServices.setUsers(UserService)          // StoredUserService
ServiceCovers
StoredLibraryServiceLibraries, members, source, save, create, copy, rename, delete, edit locks, compile, programs (kept as source and compiled again on load), storage cost (ELC0207), diskette images and restore; a member listener that FolderSync uses
StoredFileServicePhysical files and their records; ELSYS's live files through LiveFiles
StoredJobServiceInteractive jobs (in memory, per session) and batch jobs (saved), the job queue and dispatch to hosts, hold, release, end and change, logs and ended jobs' logs, call stacks from the VM, schedule entries, triggers, *JOBCTL checks
StoredMessageServiceMessage queues (one per user, QSYSOPR for *SYSOPR), unread counts, the cap, chat notices
StoredSpoolServiceSpooled files, the cap, printing through Printers
StoredSysvalServiceSystem values with their defaults and allowed values; only changed values are stored; *SECOFR to change
StoredUserServiceUser profiles, sign-on (ELC0402), *SECOFR, whether sign-on and authority checks apply (SECLVL), who may manage whose jobs

Tests#

TestCovers

Because three tests (CompilerTest, VmTest, EditorTest) go through every file in docs/elcl/examples, and CompilerTest checks how many there are, add new examples there only together with that count.

Game tests run with ./gradlew runGameTestServer (registered in gametest/EncodedLogisticsGameTests). The Terminal OS ones are in ElclGameTests (OS commands, completion messages, screen queries), ElclVmGameTests (the mod commands on Command Entry, CALL, the examples running), ElclStoreGameTests (persistence, storage, caps, authority), DeviceNameGameTests, BatchJobGameTests, SchedulingGameTests, SecurityGameTests, DatabaseGameTests, FolderSyncGameTests, InterfaceGameTests (diskettes, printers and recipe libraries against fakes), DeskGameTests, CraftHistoryGameTests, and for the devices ControlInterfaceGameTests, PlcGameTests, DisplayGameTests, SignalGameTests and ArcforgeGameTests (only with Arcforge in the run).

Not automated: rendering in each phosphor at every GUI scale.
