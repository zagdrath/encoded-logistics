Schedulers

The Scheduler multiblock and the rack Scheduler - what plans and runs crafting jobs, how threads and job memory work, and how jobs share them.

On this page
  1. The Scheduler multiblock
  2. Forming rules
  3. The Core's screen
  4. Threads and job memory
  5. The rack Scheduler
  6. Which host a job goes to

A Scheduler runs crafting jobs. When you ask the network for something it plans the job, then hands it to a Scheduler, which holds the ingredients, works through the steps, offers each one to a provider and collects the results. A network can have several.

There are three kinds of job host:

HostBuilt fromWhere
A SchedulerA multiblock of Scheduler Core, Job Buffers and Thread UnitsBelow
The rack SchedulerCompute and Memory Servers (and Blades) in Server RacksBelow
A Midrange SystemOne block, crafting its own diskette recipesThe Midrange line

Each has threads (how much crafting it keeps going at once) and job memory (how big a job it can take).

The Scheduler multiblock#

A Scheduler is built from three blocks:

BlockAdds
Scheduler CoreThe one block every Scheduler needs: autocrafting.schedulerBaseThreads (default 1) thread and autocrafting.schedulerBaseMemory (default 4096) job memory on its own
Job Bufferautocrafting.jobBufferMemory (default 16,384) job memory each
Thread Unitautocrafting.threadUnitThreads (default 1) thread each

Forming rules#

Touching Scheduler blocks form one Scheduler when:

  1. they fill their bounding box: a solid cuboid, no gaps, no other blocks inside;
  2. no side is longer than autocrafting.schedulerMaxSize (default 7) blocks;
  3. they contain exactly one Scheduler Core.

Mix Job Buffers and Thread Units however you like. A formed Scheduler's blocks change to their connected look. It's checked again whenever one of its blocks is placed or broken. If it doesn't form, the Core's screen says why: no Scheduler Core, two or more Cores, not a solid cuboid, or too large.

A formed Scheduler is one network device: cables connect to any of its blocks, the Core uses one lane, and it drains autocrafting.schedulerDrain (default 2) FE a tick plus autocrafting.schedulerDrainPerBlock (default 0.5) per block. Nothing runs while it's unformed or offline. Thread Units glow while jobs run.

Breaking the Core fails its jobs

Everything the Scheduler's jobs are holding drops at the Core, and the jobs end as failed. Breaking a Job Buffer or Thread Unit unforms the Scheduler until you put it back.

The Core's screen#

Use any block of a formed Scheduler to open it. It shows:

  • the running jobs (item, amount, progress, and an × to cancel each) and the queue;
  • a threads meter and a job buffer (memory) meter;
  • the last five jobs that finished there (hover one for what it made, when, how long it took and why it failed), with a pointer to the full crafting history.

Click a job to open its Job Status screen.

Threads and job memory#

Job memory is the number of items across a job's whole ingredient tree. A job is accepted only when its memory fits in what the host has free; a Scheduler with 4,096 memory can take a job needing 3,000 items' worth of steps alongside one needing 1,000. When nothing has room, the plan screen says "No Scheduler has room".

Threads are shared among the jobs:

  • Every queued job gets a thread first, so a big job never blocks a small one. If no thread is free, the job with the most gives one up.
  • Free threads then go round the running jobs that can use more, one at a time.
  • Each thread keeps autocrafting.threadCrafts (default 1) craft going at once (0 means no limit). A job wants as many threads as it has crafts left, divided by that. Fabricators and Fabrication Servers run every craft they're given side by side, so a job holding twelve threads makes twelve crafts at a time.
  • A job gives threads back as it nears its end, so the next job can start.

So the way to speed jobs up is more threads (Thread Units, Compute Servers) and more providers with the same schematic (each run goes to the least busy one: see several machines).

The rack Scheduler#

Server Racks have their own Scheduler, built from rack devices:

DeviceGives
Compute Serverrack.computeServerThreads (default 2) threads
Memory Serverrack.memoryServerMemory (default 32,768) job memory
Compute Blade, Memory Blade in a Blade EnclosureThreads and memory as their servers give per rack unit, optical.bladeBonusPercent (default 25) % more

They pool across every rack on the network: all the online Compute and Memory Servers and Blades serving a network, in whichever of its racks, make one rack Scheduler with all their threads and memory added up. You don't need a Memory Server in the same rack as each Compute Server, and you don't get one Scheduler per rack.

  • The pool runs jobs once it has both threads and memory.
  • It appears on the plan screen's Scheduler choices as "Rack x, y, z": the rack that heads the pool (the first rack with an online Compute Server serving the network). If the head changes, its jobs move to the new head and carry on.
  • It offers crafts to the network's Fabrication Servers and Fabrication Blades first, then to the other providers.
  • Compute Servers blink while jobs run on the pool; Memory Servers while jobs hold memory.
  • Breaking the head rack fails its jobs, as breaking a Core does.

The servers and blades themselves are on Rack devices and Modular chassis.

Which host a job goes to#

The plan screen's Scheduler selector starts at Auto, which picks the first host with a free thread and room for the job's memory, or failing that the first with room (the job then waits in its queue). You can cycle it to pick a particular Scheduler, the rack Scheduler or a Midrange System instead. See Crafting jobs.
