Terminal OS and ELCL Reference

The Encoded Logistics Terminal Desk runs a small midrange-style operating system, the Terminal OS, and a control language, ELCL (Encoded Logistics Control Language). This page covers using the terminal and its screens, writing and compiling ELCL programs, running programs as interactive and batch jobs, schedules and triggers, every command and message, the Control Interface block, the server config, and the hardware that is still to come.

It is written for players and server admins, with a short section for mod contributors at the end. The design documents live in docs/elcl/; where they and the code disagree, this page describes what the code does and points out the difference.

1. Overview

The Terminal Desk, the Terminal OS, ELCL and the Control Interface

Terminal Desk
The block you sit at. Its screen is an 80 by 24 green-screen terminal with function keys, a command line and a message line. It works on the network it is connected to, and has a drawer that withdrawn items can go to.
Terminal OS
The operating system the desk shows. It keeps libraries of source members and compiled programs, runs jobs, keeps job logs, user message queues, spooled files (printed output) and system values, and has a screen for each of these. The desk's original screens (inventory, crafting jobs, devices, network status) are part of its Main Menu.
ELCL
The Encoded Logistics Control Language. It is modelled on midrange control languages: every statement is a command with keyword parameters such as CRTLIB LIB(ZAGLIB) TEXT('My scripts'), variables start with &, special values start with *, and errors are handled with MONMSG. You type ELCL commands on any command line, and you write ELCL programs in source members, edit them in the source editor and compile them. The same command definitions drive the parser, the compiler, the F4 prompter, F1 help and the command line.
Control Interface
A network device block that gives ELCL redstone input and output: six faces, each readable with RTVRSIN and drivable with CHGRSOUT. It has no GUI of its own; it is named CTLIF01, CTLIF02 and so on, and is driven from the terminal. See section 9.

Read this first. Everything on this page works: the screens, the command line, libraries and members, the editor and compiler, running programs (interactively with CALL, or as batch jobs on Compute Servers), schedule entries and triggers, sign-on and Firewall authority, and every inventory, crafting, device, power and redstone command. What the OS keeps is saved with the world, per network.

The Midrange line is in: its Line Printer prints, its 8" Diskettes take SAVLIB, and its Midrange Systems run batch jobs and crafting (the Midrange line). A few commands still talk to hardware that isn't in the mod yet (the Mainframe, the display blocks). They are built and tested against interfaces, and answer ELC1301 Device &1 not found. until that hardware exists. See section 10.

Systems and networks

Each network is one system. Its libraries, jobs, message queues, spooled files and system values belong to that system, and every desk on the network sees the same ones.

  • The name in the top right of every screen (System: ELNET01) is the network's name, ELNET followed by the network's two-digit number. A desk that isn't on a network shows *OFFLINE.
  • The system value SYSNAME starts out as the same name. Changing it does not change the screen header (which always shows the network name); SYSNAME appears in compile listings, printed members and reports, saved diskette images, and names the system's sync folder.
  • While a desk has no network, OS commands and screen requests answer ELC1302 Device *NETWORK is offline.

What is saved

Each system's data is saved with the world (in the overworld's saved data, one record per network, keyed by its controller structure) and loaded with it:

  • libraries, source members (with their sequence numbers and change dates) and compiled programs (kept as source with their compile date and source version, and compiled again on load);
  • message queues, spooled files and system values;
  • batch jobs: queued, held and running ones, a running one with its whole VM state; the logs of the last LOGRTN ended jobs; job schedule entries and trigger events, with the player who made each;
  • the crafting job history: a record of each of the last CRFLOGRTN crafting jobs that ended (see crafting job history);
  • user profiles (library list, current library, last sign-on) and which device holds each device name.

Not saved: interactive jobs (they belong to an open terminal session and end with it) and member edit locks. ELSYS is never saved: it is rebuilt from the mod's bundled examples, and its programs compiled, every time a system is made or loaded, so a mod update brings new samples with it.

Two caps keep a system's data in bounds (server config, section 10): at most 200 spooled files per system and 500 messages per user's queue; past either, the oldest go first. Source members also cost network storage.

Signing on

The Sign On screen appears when you open a desk on a network that has a Firewall, unless the system value SECLVL is 10. Without a Firewall there is no sign-on: the desk opens on the Main Menu (and everyone has full authority anyway). Signing on happens on the server: until the session has signed on, the desk answers nothing but the screen's system information and the sign-on itself, so another screen can't be reached around it.

User
Your own player name, in any case. There is no password. Any other name is refused by the server with ELC0402: Sign-on failed for user NAME. on the message line, and the field is cleared; a blank one gives "Type your user name."
Program/procedure
A program to CALL straight after sign-on (LIB/NAME, or a name on your library list). Blank or *NONE: none. It runs in your interactive job like a CALL typed on the command line (running a program).
Menu
The menu to start on. MAIN is the only one; anything else gives "Menu X not found. MAIN is the menu there is."
Current library
Where new members go, where a name that isn't on your library list is looked for, and what WRKMBR shows when no library is given. *USRPRF (the default) keeps your profile's (ELGPL until you change it). A library name is checked on the server (ELC0201 if there's none), saved in your profile and put first on your library list.

Enter signs on ("Signed on as NAME."); the first sign-on makes your user profile if you haven't one yet. Esc, F3 or F12 on the Sign On screen closes the terminal.

Users, security and the Firewall

  • User. Commands always run as the player at the desk, as their name in upper case (ZAGDRATH). Signing on does not let you become someone else.
  • User profiles. Each player has a profile on each system, made the first time they use a terminal there or sign on, and saved with the system: their library list (ELGPL ELSYS to start with, with the current library first), current library, when it was made and their last sign-on.
  • *SECOFR. The security officer class: the Firewall's owner (the network's owner) and server operators while they're online. Everyone else is a plain user. The class is worked out each time, so a new Firewall owner takes effect at once.
  • Interactive job. Each open desk session has an interactive job named QINTER, started by the session's first request and ended (with ELC0307 in its log) when you close the terminal; a program it is running ends with it. Closing also releases any member edit locks you hold.
  • Authority comes from the Firewall. Each command has a required Firewall permission: none, view, insert, extract, craft, or configure (the Firewall's build permission). If you lack it the command fails with ELC0401 Not authorized: user &1 lacks &2 permission., where &2 is the Firewall permission name (VIEW, INSERT, EXTRACT, CRAFT or BUILD). One check serves everything: commands on the command line, commands inside programs, the OS screens (whose data needs view) and their options. Server operators at a terminal may do everything.
  • Batch jobs run as their submitter. A batch job, and a job submitted by a schedule entry or trigger, is checked against the Firewall's permissions for the player who submitted or created it, by their player id, whether they are online or not.
  • No Firewall: full authority. Every player who can open a desk can do everything (single-player friendly). With a Firewall, its per-player permissions and its default policy for unknown players apply. An offline Firewall still enforces its rules unless the config option firewallFailClosed is turned off.
  • Changing system values (CHGSYSVAL, Work with System Values 2=Change) takes *SECOFR, or a network with no Firewall; otherwise ELC0401 names *SECOFR.
  • Other users' jobs. Holding, releasing, ending or changing another user's job, schedule entry or trigger takes *SECOFR (or full authority: no Firewall, or SECLVL 10); otherwise ELC0401 names *JOBCTL. Your own are always yours to manage.
  • Library authority. ELSYS is read-only for everyone (ELC0205). ELGPL has public authority *CHANGE, so everyone can change its members. A new library is owned by its creator with public authority *USE: others can read it but not change it (ELC0401 naming *CHANGE) unless the owner sets *CHANGE. Only the owner may change a library's text or authority or delete it (ELC0401 naming *OWNER). *SECOFR may do all of these in any library but ELSYS, and anyone may change the text and authority of a library the system owns (QSYS: ELGPL, and libraries made by folder sync).

The command line

Every screen with ===> takes commands. What you type is handled in this order:

  1. On a menu, a number is the menu option. In the editor, editor commands (FIND, SAVE...) come first.
  2. clear (any case) clears Command Entry's history.
  3. A command that opens a screen (WRKLIB, WRKMBR LIB(ZAGLIB), DSPMSG, GO MAIN, SIGNOFF... see screen commands) is checked against its schema and opens the screen on this desk.
  4. Otherwise the line goes to the server and runs as an ELCL command in your interactive job. (The desk's old words are gone: see the desk's old words.)

An ELCL command on the command line is parsed, checked against its schema, checked for where it may run and for Firewall authority, then run. Its messages are shown as ID text (escape and completion messages bright), the values of any RTN* parameters are listed as RTNLVL = 7, and the last message goes to the message line. If the command produced output and you're not on Command Entry, Command Entry opens to show it. The command and its messages also go in your interactive job's log.

CALL on the command line starts the program in your interactive job and answers at once (ELC0108 Program LIB/NAME running in job ...); its messages come to Command Entry when it ends. See running a program. DLYJOB typed on a command line has nothing to hold up and completes at once.

There are no variables on the command line (an &name is ELC0002), but expressions of literals work, for example SNDMSG MSG('Shift' *BCAT 'change'). RTN* parameters are optional on the command line even when a program would have to give them. Language statements such as DCL, IF or CHGVAR answer ELC0106 there.

Tab completion (Command Entry only) completes the first word from the ELCL command names and later words from the network's item names; F4 prompts a command's parameters. One match fills in the word; several are listed on the message line.

The prompter (F4)

Type a command name (with or without some parameters) on a command line and press F4. The prompter shows one row per parameter, built from the command's schema.

  • The title is the command's description and name. Each row has the label with dot leaders (bright when the parameter is required), the keyword (dim), the input field (the schema's length, at most 24 shown; longer values scroll) and a hint (dim) such as 1-999999, *FAIL, *PARTIAL, Name, F4 for list, *CHAR variable.
  • Required parameters come first. The others sit under Additional Parameters, shown with F10 or as soon as any of them has a value.
  • A list parameter (hint + for more values) takes several values separated by blanks; typing just + and pressing Enter opens a window with four value fields.
  • F4 on a field opens its value list, Select Value - label: special values first, then what the server lists for that kind of parameter (items in the network, filtered by what's typed in the field, up to 200; devices; libraries; members and programs in ELGPL and ELSYS; jobs; system values). Type 1 next to one and press Enter (or double-click it). On a command parameter (SBMJOB CMD, ADDJOBSCDE CMD, or IF THEN in the editor) F4 opens the prompter for the nested command instead.
  • Enter checks the values: a missing required value (ELC0102), a value not valid for a parameter (ELC0103) or out of range (ELC0004) is shown on the message line and the cursor goes to that field. When it's clean the prompter builds the command (keywords in schema order, values left at their defaults are left out, text quoted where needed).
  • From Command Entry, the built command is put back on the command line for you to press Enter. From any other screen's command line it runs straight away. From the editor it replaces the statement in the source.
  • F5 resets every value to its default. F3 and F12 return without a command. F1 on a field explains that parameter: what it takes, its special values, its default and whether it is required; F1 elsewhere lists all the command's parameters (required ones marked *).

Help windows (F1)

F1 opens a window titled "Screen title - Help" over the current screen with help for the field under the cursor, or the screen's help if the field has none. In lists, the Opt column has its own help listing the options. In the prompter, help comes from the command's schema. GO HELP on a command line opens the same window. The window's keys are F3=Exit help F12=Cancel; Page Up / Page Down scroll it. A screen without help text says "No help is available for this screen. Press F12 to return."

Phosphor colours

The screen can be drawn in green, amber or white phosphor. Each player chooses on More Keys and Settings (F24): Green, Amber, White or *SYSVAL (type the word, its start, or 1–4). The choice is kept in the client config. The default, *SYSVAL, follows the system value PHOSPHOR (*GREEN, *AMBER or *WHITE; default *GREEN), so a server admin can set every terminal's colour on a system at once. A change made on Work with System Values takes effect on that desk straight away.

How option lists work

4. Libraries, members and the editor

Libraries and members

Library
A named container of source members and programs. Names are up to 10 characters: a letter, then letters, digits, _, @, # or $. Types are *PROD or *TEST (CRTLIB TYPE()), and *SYS for ELSYS. A library records its owner, public authority (*USE or *CHANGE), text and creation time.
ELSYS
The read-only system library that ships with the mod. It holds the sample programs ARCHIVE, NOCWALL, RESTOCK, SORTDEMO and UPSALERT (from data/encodedlogistics/elcl/ELSYS/, the same files as docs/elcl/examples/), each already compiled, so CALL ELSYS/RESTOCK PARM('IRON_INGOT' 500) works on a new system. Browse them with 5=Display, copy them with 3=Copy, compile them into one of your libraries. ELSYS is rebuilt from the mod every time the system loads, and never costs storage.
ELGPL
The general purpose library on every system, public authority *CHANGE. It can't be deleted.
Source member
Type ELCLP. Lines of up to 80 columns, each with a sequence number in 6.2 form (0012.00, up to 9999.99) and a change date (the game day it last changed). A member's text is its description.
Program
A compiled *PGM, recording its source member, the source it was compiled from and its compile date. It runs with CALL (running a program). Changing the member afterwards doesn't change the program: Work with Members flags the member with * in the Chg column until you compile it again.
Library list
Each user profile has a library list, ELGPL ELSYS to start with. A bare name or *LIBL/NAME is looked for in those libraries in that order; if it isn't found, the current library is used (a new member goes there). *CURLIB is the profile's current library, ELGPL until you choose another on the Sign On screen, which also puts it first on the list. CALL looks for programs down the same list (ELC0203 naming *LIBL if none has it).
Edit locks
One user edits a member at a time. Opening it in the editor while someone else has it gives ELC0208 Member &1 is locked by another user. and the editor opens read-only. Locks are released when you leave the editor or close the terminal.

Libraries, members and programs are saved with the system (what is saved). Source costs network storage (storage cost), members can be edited outside the game (folder sync), and a library can be saved to and restored from an 8" Diskette (saving to diskette).

The source editor (EDTMBR)

  • Row 1: the member (LIB/NAME) and its type. Row 2: the columns shown, and the cursor's line and column. Row 3: the column ruler, when it's on (COLS or F15).
  • Each source row has a 7-character margin holding the sequence number (type a line command over it) and the line's text, 72 of its 80 columns at a time. New lines show ''''''' in the margin until they are saved.
  • Beginning of data and End of data mark the ends; a run of excluded lines shows as one row, "N data records excluded".
  • Type over the text to change it. The Insert key switches between overwrite and insert.
  • Opened read-only (WRKMBR 5=Display, a member in ELSYS, a library you can only read, or a member someone else is editing) the title is Display Member, every field is protected, and the command line takes only FIND, TOP and BOTTOM.

Syntax check

Each Enter checks the statements you changed (with their continuation lines) through the ELCL parser and compiler. The first error in a changed statement is shown reversed, the cursor goes to it, and its message goes on the message line, for example ELC0002: Variable &CONT is not declared. Saving is still allowed with errors; compiling is what refuses them.

Compiling

Compile with WRKMBR option 14, or CRTELPGM PGM(LIB/NAME) SRCMBR(*PGM|LIB/NAME). SRCMBR(*PGM) (the default) compiles the member with the program's own name. The program's library must be one you can change (compiling into ELSYS is ELC0205). The compiler checks:

  • PGM first and ENDPGM last; DCLs before anything else (ELC0016); program-level MONMSGs straight after them.
  • Every variable declared (ELC0002) and of a type its use takes (ELC0003); declarations valid (no duplicates; *CHAR length 1–1024; *DEC length 1–31 with decimals not more than the length; LEN only on *CHAR and *DEC; no VALUE on a *LIST).
  • Every command's parameters against its schema: required (ELC0102), special values and kinds (ELC0103), ranges (ELC0004), not given twice (ELC0104), RTN* parameters given variables of the right type.
  • Blocks matched (DO/ENDDO, FOREACH/ENDFOR, SELECT/ENDSELECT, SUBR/ENDSUBR), ELSE after its IF, WHEN inside a SELECT, LEAVE and ITERATE inside a loop (ELC0009).
  • Every GOTO label exists (ELC0010) and isn't inside a loop or DO group the GOTO is outside of (ELC0014).
  • Literal problems it can see: division by a literal zero (ELC0005), numeric overflow (ELC0007), a literal too long for a *CHAR (ELC0008, a warning).

Any message of severity 20 or more means no program: ELC0206 Program &1 was not created: compile errors. Otherwise ELC0218 Program &1 created in library &2. Either way the listing goes to Work with Output as a spooled file named after the program, in your interactive job.

Run a compiled program with CALL PGM(LIB/NAME) on any command line, or submit it as a batch job with SBMJOB CMD(CALL PGM(LIB/NAME)). See running a program.

Storage cost

Source members take room on the network's drives: one byte of drive space per 64 characters of source, rounded up per member (server config charsPerStorageByte). ELSYS, compiled programs, job logs and spooled files cost nothing.

  • Saving a member, creating, copying or restoring one, or a folder-sync import, that needs more than the drives have free fails with ELC0207 Not enough network storage to save &1. A network with no drives at all can only hold empty members.
  • The bytes the members take count as used hot storage on Display Network Status, in RTVSTGSTS and for the *STGFULL trigger. Work with Libraries 5=Display shows a library's size in characters.
  • Known limit: the space is counted, not reserved. Items going into the network don't check for it, so a network can fill its drives with items past the point where its members fit; then only saves that make a member smaller (or delete one) go through until space is freed.

Folder sync

A system's libraries can also live as plain files in the world save, so you can edit members in any text editor or keep them under version control:

<world>/encodedlogistics/libraries/<SYSNAME>/<LIB>/<MEMBER>.elclp
  • Out: saving a member in the editor, and creating, copying, renaming or restoring one, writes its file at once.
  • In: while the network is loaded the folder is read every two seconds. A new or changed file becomes the member: lines that didn't change keep their sequence numbers and change dates, changed and new lines are numbered between their neighbours and dated today (if there's no room, the member is numbered again in steps of 1.00). A new folder becomes a library, owned by the system (QSYS) with public authority *CHANGE.
  • Conflicts: the system remembers what it last synced for each member, so a file and a member that both changed since are a conflict. The last write wins (an in-game save is always the later one), and the losing version is kept beside it as <MEMBER>.elclp.bak.
  • Deletes: deleting a file never deletes its member (for safety). Deleting a member in the game moves its file to <LIB>/.deleted/.
  • ELSYS is never synced, in or out: it comes from the mod.
  • The folder is named after SYSNAME, so changing that system value starts a new folder.
  • Server config allowFolderSync: AUTO (the default: on in single-player, off on dedicated servers), TRUE or FALSE.

Saving to diskette (SAVLIB / RSTLIB)

SAVLIB LIB(ZAGLIB) DEV(MIDRANGE01) writes a library (its members with their sequence numbers and dates, and its programs) to the 8" Diskette in a diskette drive; RSTLIB LIB(ZAGLIB) DEV(MIDRANGE01) restores it, on this system or any other. Diskettes are items, so a library can be carried to another network or handed to another player.

  • SAVLIB writes to the first diskette in the drive, replacing a library of the same name on it: ELC0220 Library &1 saved to &2., where &2 is the device and the diskette's label. A diskette holds 64 KB of source (server config disketteBytes); a library that won't fit in what's free is ELC1311 Library &1 needs &2 bytes; the diskette has &3 free.
  • RSTLIB reads from the first diskette holding that library (ELC0201 if none does). It creates the library, owned by you, or replaces an existing one's members and programs (that needs *CHANGE on it: ELC0401); it never writes to ELSYS (ELC0205), and the members must fit in the network's storage (ELC0207). Programs are compiled again from their saved source. ELC0221 Library &1 restored from &2.
  • No such device is ELC1301, an offline one ELC1302, a drive with no diskette ELC1310 No diskette in device &1.

The drives are the Midrange System (its diskette slot, and a second with an Expansion Cabinet), the Integrated Midrange System (every diskette in its magazine) and the Card Reader. Their names are MIDRANGE01 and CARDRDR01 unless renamed. The library is kept on the diskette item, so it goes wherever the diskette goes. See the Midrange line.

5. The ELCL language

ELCL is a small, sandboxed control language modelled on midrange control languages. A program is a list of commands with keyword parameters. Extensions that real CL doesn't have are marked [EXT] in the spec (docs/elcl/ELCL_SPEC.md); this section follows it, with notes where the code goes further or differs.

Lexical rules

Case
Case-insensitive. Keywords, command names, variable names, labels, special values and built-in names are folded to upper case. The contents of string literals keep their case.
Comments
/* ... */. They may span lines and do not nest.
Statements and continuation
A statement ends at the end of its line, unless the line's last token is + or - (comments after it are allowed): then the statement carries on with the next line. Inside a string literal, + as the last character of the line continues the string with the next line exactly as it is; - continues it with the next line's leading blanks dropped.
Labels
NAME: at the start of a statement, up to 10 characters (a longer one is ELC0001). A label may also stand alone on its own line; it then belongs to the next statement.
Names
Letters, digits, _, @, #, $; they start with a letter. Command names, labels, library, member and program names: up to 10 characters. Variables: & followed by a name, up to 32 characters in all.
String literals
Single quotes, with '' for an embedded quote: 'Can''t find item'.
Numbers
42, -7, 3.25. No underscores. A - straight before a digit, after a blank or ( (or at the start of a statement), is a negative number: PARM(&A -5) is two values, while &A - 5 and &A-5 both subtract.
Special values
* followed by a name: *YES, *ALL, *HOT. Which ones a parameter accepts is part of its schema (see the command reference). Inside a value, * straight before a letter is a special value or operator word; * followed by a blank or a digit is multiplication.
Qualified names
LIB/NAME for programs and members, for example ELGPL/RESTOCK. *LIBL (or no library) searches your library list.
Item IDs
Quoted or unquoted: IRON_INGOT, 'minecraft:iron_ingot', 'encodedlogistics:logic_die'. By the spec, an unqualified ID resolves first to minecraft:, then encodedlogistics:, then any unique match, and is ELC1205 if more than one mod has it. Tags in filters use #: '#c:ingots'. Item IDs come back from commands (RTVITMLST) the same way: a minecraft: item as its path in upper case (IRON_INGOT), any other in full (encodedlogistics:logic_die).
Keyword and positional parameters
A keyword is a name followed directly by ( with no blank: LIB(ZAGLIB). Values without keywords go to the command's positional parameters in order, and only before the first keyword: RTVRSIN CTLIF01 *NORTH RTNLVL(&L).
Characters you can type
The terminal only accepts printable ASCII, so the ¬ operator can't be typed in the editor; use *NOT (and *NE or <> for not-equal).

Program structure

PGM PARM(&ITEM &MIN)            /* optional parameter list          */
  DCL VAR(&COUNT) TYPE(*INT)    /* declarations come first          */
  MONMSG MSGID(ELC1201) EXEC(GOTO CMDLBL(NOITEM))  /* program-level */
  ...commands...
NOITEM:
  SNDMSG MSG('Item not found') TOUSR(*REQUESTER)
ENDPGM
  • Every program starts with PGM and ends with ENDPGM.
  • DCL statements come before any other command (ELC0016 otherwise). Parameters named on PGM PARM() must be declared too.
  • Program-level MONMSG statements come directly after the DCLs.
  • Subroutines (SUBR ... ENDSUBR) go after the main body, before ENDPGM.
  • Source members have type ELCLP and compile to a *PGM.

Grammar

From the spec (EBNF):

program     = "PGM" [ "PARM" "(" { variable } ")" ] NL
              { declaration NL }
              { monmsg NL }
              { statement NL }
              "ENDPGM" ;

declaration = "DCL" "VAR" "(" variable ")" "TYPE" "(" type ")"
              [ "LEN" "(" integer [ integer ] ")" ]
              [ "VALUE" "(" value ")" ] ;

type        = "*CHAR" | "*INT" | "*DEC" | "*LGL" | "*LIST" ;

statement   = [ label ":" ] command [ NL monmsg { NL monmsg } ] ;

command     = name { parameter } ;
parameter   = keyword "(" value { value } ")"   (* keyword form   *)
            | value ;                           (* positional form *)

value       = expression
            | special
            | qualified
            | "(" command ")"                   (* nested command, only in
                                                   THEN, EXEC, CMD, ELSE CMD *)
            ;

expression  = orExpr ;
orExpr      = andExpr { ("*OR" | "|") andExpr } ;
andExpr     = notExpr { ("*AND" | "&") notExpr } ;
notExpr     = [ "*NOT" | "¬" ] relExpr ;
relExpr     = catExpr [ relop catExpr ] ;
relop       = "*EQ" | "=" | "*NE" | "<>" | "*GT" | ">" | "*LT" | "<"
            | "*GE" | ">=" | "*LE" | "<=" ;
catExpr     = addExpr { ("*CAT" | "||" | "*BCAT" | "|>" | "*TCAT" | "|<") addExpr } ;
addExpr     = mulExpr { ("+" | "-") mulExpr } ;
mulExpr     = unary { ("*" | "/" | "//") unary } ;   (* // = integer remainder *)
unary       = [ "-" ] primary ;
primary     = literal | variable | builtin | "(" expression ")" ;
builtin     = "%" name "(" [ expression { expression } ] ")" ;

Notes:

  • Whether a parameter takes an expression, a special value, a qualified name or a nested command is defined by its schema. The parser resolves positional parameters using the schema's positional order.
  • A nested command is written in the parameter's own parentheses: THEN(CHGVAR &Y 1), EXEC(GOTO CMDLBL(DONE)). These can't be nested: PGM, ENDPGM, DCL, ENDDO, ENDFOR, SELECT, ENDSELECT, SUBR, ENDSUBR, ELSE, WHEN, OTHERWISE, MONMSG.
  • The code also accepts *NG (not greater, same as *LE), *NL (not less, same as *GE) and ¬= (same as <>).
  • Each statement's first problem is reported and the rest of that statement skipped: ELC0001 (syntax), ELC0101 (unknown command), ELC0104 (a keyword given twice).

Control flow

IF COND(&A *GT 10) THEN(DO)
  ...
ENDDO
ELSE CMD(DO)
  ...
ENDDO

IF COND(&X *EQ 0) THEN(CHGVAR &Y 1)
ELSE CMD(CHGVAR &Y 2)

DOWHILE COND(&I *LT 10)  ... ENDDO
DOUNTIL COND(&DONE)      ... ENDDO      /* body runs at least once */
DOFOR VAR(&I) FROM(1) TO(10) BY(1)  ... ENDDO
FOREACH VAR(&E) IN(&LIST)  ... ENDFOR    /* [EXT] */
LEAVE [CMDLBL(label)]      /* exit innermost or labelled loop */
ITERATE [CMDLBL(label)]    /* next iteration */

SELECT
  WHEN COND(&T *EQ 'NAS') THEN(...)
  WHEN COND(&T *EQ 'SAN') THEN(...)
  OTHERWISE CMD(...)
ENDSELECT

GOTO CMDLBL(label)         /* only to labels in the same program, not
                              into a loop or DO group from outside      */
RETURN                     /* end this program, back to caller          */
  • ELSE must immediately follow the IF it belongs to (or that IF's ENDDO). An ELSE elsewhere is ELC0009.
  • THEN(DO), CMD(DO) and EXEC(DO) open a DO group closed by ENDDO.
  • DOFOR: VAR must be a *INT variable; FROM and TO are required; BY defaults to 1. FOREACH: VAR is a *CHAR variable, IN a *LIST.
  • LEAVE and ITERATE must be inside a loop. Their CMDLBL defaults to *CURRENT (the innermost loop); give the label of an enclosing loop to leave or continue that one: OUTER: DOFOR VAR(&I) FROM(1) TO(9) ... LEAVE CMDLBL(OUTER).
  • WHEN must be inside a SELECT. Each WHEN's THEN and the OTHERWISE's CMD hold one command or a DO group.
  • A GOTO target must exist (ELC0010) and must not be inside a loop or DO group that the GOTO is outside of (ELC0014).

Subroutines

  CALLSUBR SUBR(REPORT) RTNVAL(&RC)
  ...
  RETURN

  SUBR SUBR(REPORT)
    ...
  ENDSUBR RTNVAL(0)
ENDPGM
  • SUBR blocks go after the main body, before ENDPGM. Subroutines share the program's variables. Subroutine nesting is limited to 16.
  • ENDSUBR RTNVAL() takes an integer value (default 0); CALLSUBR RTNVAL() names a *INT variable that receives it. (The spec writes ENDSUBR [RTNVAL(&I)]; in the code that parameter is an integer value or expression, not a return variable.)
  • A CALLSUBR to a subroutine that doesn't exist is ELC0010.

MONMSG and error handling

Every failing command raises an escape message with an ID from the message reference (ELCnnnn) and message data.

  • Command-level: a MONMSG directly after a command applies to that command only. Several may follow one command, including after another MONMSG's EXEC(DO) ... ENDDO.
  • Program-level: MONMSG statements straight after the DCLs apply to every command in the program. A MONMSG anywhere else that doesn't follow a command is ELC0009.
  • MONMSG MSGID(id ...) [CMPDTA('text')] [EXEC(command)]
    • Up to 50 IDs. An ID ending in 00 monitors its whole range: ELC1200 catches ELC1201–ELC1299. ELC0000 catches everything.
    • With no EXEC, execution continues with the next command.
    • EXEC may be GOTO, DO ... ENDDO, RETURN, or any single command.
  • RCVMSG MSGTYPE(*EXCP) RTNMSGID(&ID) RTNMSG(&TEXT) reads the last escape message after it was monitored (RTNMSGDTA gives its data; MSGTYPE(*LAST) the last message of any kind).
  • SNDPGMMSG MSG('text') MSGTYPE(*ESCAPE) raises your own escape message with ID USR0001, or MSGID(USRnnnn) to choose one. A message ID is three letters and four digits.
  • Unmonitored escape message: the program ends, the message goes to the job log and to the job user's message queue, and interactive jobs show it on the message line. The caller sees ELC0013 (called program ended abnormally), which it may monitor.
  STRCRAFT ITEM(&ITEM) QTY(&MIN - &COUNT) RTNCRFJOB(&JOB)
  MONMSG MSGID(ELC1400) EXEC(DO)        /* any crafting error, ELC1401-ELC1499 */
    SNDMSG MSG('RESTOCK: cannot craft' *BCAT &ITEM) TOUSR(*SYSOPR)
    RETURN
  ENDDO

CALL and parameters

CALL PGM(LIB/NAME) PARM(&A 'text' 5) calls a compiled program. Variables are passed by reference (the called program can change them) and literals and expressions by value, as in real CL. The called program's PGM PARM(...) must have the same number of parameters (ELC0012 otherwise). Call depth is limited to 16 (ELC0011). A called program that fails unmonitored gives the caller ELC0013. When the called program returns, the values of the variables passed are copied back into the caller's. A program with no library (or *LIBL) is looked for down the user's library list; none found is ELC0203.

CALL PGM(ELSYS/RESTOCK) PARM('IRON_INGOT' 500)

Running a program

A program always runs in a job, a budget of VM instructions per server tick at a time, so a long or endless program never holds up the server. There are three ways to start one:

On a command line: CALL PGM(LIB/NAME) PARM(...)
The program runs in your session's interactive job (budget 200 instructions a tick). The command line answers at once with ELC0108 Program LIB/NAME running in job nnnnnn/USER/QINTER., and you can go on using the terminal. When it ends, the messages it sent appear on Command Entry, and the message line says how it ended: ELC0110 Program &1 ended normally. or the escape message that ended it. An interactive job runs one program at a time: a second CALL while one runs is ELC0109 Job &1 is already running program &2. Closing the terminal ends the program with its job; so does ENDJOB on the job. The Sign On screen's Program/procedure starts a program the same way.
As a batch job: SBMJOB CMD(CALL PGM(LIB/NAME)) JOB(NAME)
The program runs on a job host (budget 100 a tick), with nobody at a terminal, as the user who submitted it. See jobs.
From a schedule entry or a trigger
Each submits a batch job when it fires, as the user who added it. See schedule entries and triggers.

Inside a program, every registered command runs as it does on a command line, with the same authority checks (the job user's Firewall permissions), plus the language statements. A command that only works at a terminal (the screen commands such as WRKLIB) is ELC0105 in a batch job; in an interactive program it has nothing to run and answers ELC0107 Command &1 is not available yet. MOVITM TODEV(*DESK) needs the desk of an interactive job (ELC1301 naming *DESK in a batch job).

RTN* return parameters

Parameters whose keyword starts with RTN return a value: they must be given a variable of the stated type, which the command sets. The compiler checks the variable exists and has the right type.

RTVRSIN DEV(CTLIF01) SIDE(*NORTH) RTNLVL(&LVL)       /* &LVL is *INT */
RTVJOBA RTNUSR(&USER) RTNTYPE(&TYPE)                /* *CHAR variables */

On the command line there are no variables, so RTN* parameters are left out (even required ones) and Command Entry shows what they would have returned: RTNLVL = 7.

Limits and runtime model

  • Programs are compiled before running; running source directly is not supported. A program runs the source it was compiled from, whatever has happened to the member since.
  • Limits: 5,000 source lines per member (config maxSourceLines); 4,096 list elements (ELC0015; config maxListSize); *CHAR length 1,024; call depth 16 (ELC0011); subroutine depth 16.
  • Instruction budget: each tick, each running job executes at most its budget of VM instructions, then yields: 200 for an interactive job, 100 for each batch job, with a global cap of 2,000 per tick across all jobs on the server. Jobs take turns starting first, so the global cap is shared out fairly. All three are server config (interactiveBudget, batchBudget, globalBudget). Work with Active Jobs shows what each job used.
  • Async commands put the job into a wait (status *WAIT) that costs no budget, and the command carries on when the wait is over: DLYJOB DLY(n) (n seconds of game time, 20 ticks each, so it stretches if the server lags) or DLYJOB RSMTIME(HHMMSS) (the next time the game clock comes round to it); MOVITM of items that are partly on tape (it recalls them, sends ELC1203 and waits for them); STRCRAFT WAIT(*YES) (until its crafting job has ended). On a command line none of these wait: DLYJOB completes at once, and MOVITM / STRCRAFT start the recall or the craft and say so.
  • Runtime errors are escape messages like any other and can be monitored: list index out of range (ELC0006), division by zero (ELC0005), overflow (ELC0007), a value of the wrong type (ELC0003), the list limit (ELC0015), call depth (ELC0011), parameter count (ELC0012), a called program's failure (ELC0013). *DEC values round half up on assignment.
  • Persistence: the whole VM state (each program's position, variables, subroutine stack, loop counters, monitors, last escape message, the call stack and the wait it is in) saves to NBT with a batch job. Whether a job carries on after a restart or the loss of its host depends on the host (jobs).

Annotated examples

These are the five samples in ELSYS. All of them compile with no messages, are compiled in ELSYS already, and run (the game test elcl_examples runs each one).

RESTOCK: keep an item stocked

/* RESTOCK - keep an item stocked by crafting more when low      */
/* Usage: CALL ELSYS/RESTOCK PARM('IRON_INGOT' 500)              */
PGM PARM(&ITEM &MIN)
  DCL VAR(&ITEM)  TYPE(*CHAR) LEN(64)
  DCL VAR(&MIN)   TYPE(*INT)
  DCL VAR(&COUNT) TYPE(*INT)
  DCL VAR(&JOB)   TYPE(*CHAR) LEN(10)

  RTVITMCNT ITEM(&ITEM) RTNCOUNT(&COUNT) NOTFND(*ZERO)

  IF COND(&COUNT *LT &MIN) THEN(DO)
    STRCRAFT ITEM(&ITEM) QTY(&MIN - &COUNT) RTNCRFJOB(&JOB)
    MONMSG MSGID(ELC1400) EXEC(DO)
      SNDMSG MSG('RESTOCK: cannot craft' *BCAT &ITEM) TOUSR(*SYSOPR)
      RETURN
    ENDDO
    SNDMSG MSG('Restocking' *BCAT &ITEM *BCAT 'job' *BCAT &JOB) +
           TOUSR(*SYSOPR)
  ENDDO
ENDPGM
  • Two parameters, both declared. NOTFND(*ZERO) makes RTVITMCNT return 0 instead of raising ELC1201 for an item the network doesn't hold.
  • QTY(&MIN - &COUNT): parameters take expressions.
  • The command-level MONMSG MSGID(ELC1400) covers every crafting error (ELC1401–ELC1404) from the STRCRAFT just above it.
  • *BCAT joins with one blank; the last SNDMSG is continued onto a second line with +.

SORTDEMO: a language tour

/* SORTDEMO - language tour: SELECT, DOFOR, SUBR, list ops       */
PGM
  DCL VAR(&DEVS) TYPE(*LIST)
  DCL VAR(&DEV)  TYPE(*CHAR) LEN(10)
  DCL VAR(&STS)  TYPE(*CHAR) LEN(10)
  DCL VAR(&TYP)  TYPE(*CHAR) LEN(16)
  DCL VAR(&I)    TYPE(*INT)
  DCL VAR(&BAD)  TYPE(*INT)  VALUE(0)

  RTVDEVLST RTNLST(&DEVS)
  DOFOR VAR(&I) FROM(1) TO(%SIZE(&DEVS))
    CHGVAR VAR(&DEV) VALUE(%ELEM(&DEVS &I))
    RTVDEVSTS DEV(&DEV) RTNSTS(&STS) RTNTYPE(&TYP)
    SELECT
      WHEN COND(&STS *EQ '*ONLINE')  THEN(ITERATE)
      WHEN COND(&STS *EQ '*FAULT')   THEN(CALLSUBR SUBR(REPORT))
      OTHERWISE CMD(PRTTXT TEXT(&DEV *BCAT 'is' *BCAT &STS))
    ENDSELECT
  ENDDO

  PRTTXT TEXT(%CHAR(&BAD) *BCAT 'device(s) in fault')
  PRTRPT RPT(*SPLF)
  RETURN

  SUBR SUBR(REPORT)
    CHGVAR VAR(&BAD) VALUE(&BAD + 1)
    PRTTXT TEXT('FAULT:' *BCAT &DEV *BCAT '(' *TCAT %TRIM(&TYP) *TCAT ')')
  ENDSUBR
ENDPGM
  • DOFOR runs to %SIZE(&DEVS); %ELEM picks each element.
  • THEN(ITERATE) inside the SELECT goes on to the next pass of the enclosing DOFOR.
  • The subroutine shares &BAD and &DEV with the main body. RETURN before the SUBR keeps the main body from running into it.
  • PRTTXT writes lines to the job's spooled file; PRTRPT RPT(*SPLF) prints it on the Line Printer. With no printer on the network that last step fails with ELC1301 (unmonitored, so the program ends there); the spooled file is still in Work with Output.

UPSALERT: a trigger program

/* UPSALERT - on switch to UPS power, shed non-essential load    */
/* Install: ADDTRGEVT TRG(UPSALERT) EVENT(*PWRUPS) +             */
/*            PGM(ELSYS/UPSALERT)                                 */
PGM PARM(&EVENT &DATA)
  DCL VAR(&EVENT) TYPE(*CHAR) LEN(10)
  DCL VAR(&DATA)  TYPE(*CHAR) LEN(256)
  DCL VAR(&DEVS)  TYPE(*LIST)
  DCL VAR(&DEV)   TYPE(*CHAR) LEN(10)
  DCL VAR(&CHG)   TYPE(*DEC)  LEN(5 1)

  MONMSG MSGID(ELC1300)    /* ignore device errors, keep going */

  RTVPWRSTS RTNCHG(&CHG)
  SNDMSG MSG('Running on UPS, charge' *BCAT %CHAR(&CHG) *TCAT '%') +
         TOUSR(*ALL)

  /* Disable every Deployer and Collector Plane */
  RTVDEVLST TYPE(DEPLOYER) RTNLST(&DEVS)
  FOREACH VAR(&DEV) IN(&DEVS)
    CHGDEVSTS DEV(&DEV) STATUS(*DISABLE)
  ENDFOR
  RTVDEVLST TYPE(COLLECTOR) RTNLST(&DEVS)
  FOREACH VAR(&DEV) IN(&DEVS)
    CHGDEVSTS DEV(&DEV) STATUS(*DISABLE)
  ENDFOR

  CHGRSOUT DEV(CTLIF01) SIDE(*ALL) LVL(15)   /* alarm lamp on */
ENDPGM
  • A trigger program receives two parameters, &EVENT (*CHAR 10) and &DATA (*CHAR 256). Event names longer than 10 characters arrive cut short in a *CHAR 10: *DEVOFFLIN, *PWRRESTOR.
  • The program-level MONMSG MSGID(ELC1300) (right after the DCLs) ignores every device error for the whole program.
  • FOREACH ... ENDFOR walks a list. CHGRSOUT SIDE(*ALL) LVL(15) powers every face of the Control Interface.

NOCWALL: a long-running batch job

/* NOCWALL - refresh a status display every 30 seconds           */
/* Submit: SBMJOB CMD(CALL PGM(ELSYS/NOCWALL)) JOB(NOCWALL)      */
PGM
  DCL VAR(&USED)  TYPE(*INT)
  DCL VAR(&TOTAL) TYPE(*INT)
  DCL VAR(&PCT)   TYPE(*DEC) LEN(5 1)
  DCL VAR(&LUSED) TYPE(*INT)
  DCL VAR(&LTOT)  TYPE(*INT)
  DCL VAR(&SRC)   TYPE(*CHAR) LEN(10)

  MONMSG MSGID(ELC1301) EXEC(RETURN)   /* display removed: stop */

  DOWHILE COND(*TRUE)
    RTVSTGSTS RTNUSED(&USED) RTNTOTAL(&TOTAL) RTNPCT(&PCT)
    RTVLANES  RTNUSED(&LUSED) RTNTOTAL(&LTOT)
    RTVPWRSTS RTNSRC(&SRC)

    SNDDSPTXT DEV(NOCDSP01) TEXT('STORAGE' *BCAT %CHAR(&PCT) *TCAT '%') +
              LINE(1) CLEAR(*YES)
    SNDDSPTXT DEV(NOCDSP01) TEXT('LANES  ' *BCAT %CHAR(&LUSED) *TCAT '/' +
              *TCAT %CHAR(&LTOT)) LINE(2)
    SNDDSPTXT DEV(NOCDSP01) TEXT('POWER  ' *BCAT &SRC) LINE(3)

    DLYJOB DLY(30)
  ENDDO
ENDPGM
  • DOWHILE COND(*TRUE) loops forever; DLYJOB DLY(30) waits 30 seconds without using the job's budget.
  • The program-level MONMSG ... EXEC(RETURN) ends the job cleanly when the display is removed.
  • Meant to run as a batch job with SBMJOB (CMD takes a nested command). It shows *WAIT on Work with Active Jobs for most of its life.
  • The mod has no display blocks yet, so NOCDSP01 isn't found: the first SNDDSPTXT raises ELC1301 and the program-level monitor ends the job at once.

6. Command reference

Every command registered in elcl/cmd/BuiltinCommands.java: 99 in all. The schemas match docs/elcl/COMMANDS.md except where noted in Not in COMMANDS.md and section 12.

Reading the tables

  • Parameters are listed in schema (keyword) order. P1, P2... mark the positional ones: those values may be given without their keyword, in that order. req = required; dft = default; special values are listed; ranges are inclusive. list(n) = up to n values. len is the prompter's field length.
  • Kinds: text (a *CHAR expression), number (an integer expression), logical (a condition), name (up to 10 characters, bare, quoted or a variable), qualified (LIB/NAME or NAME), item, device, special (one of the listed values), message ID, label, variable, command (a nested command), value (anything), time (HHMM or HHMMSS). returns *TYPE marks an RTN* parameter that needs a variable of that type.
  • Where: Program = only inside a program (on the command line: ELC0106); Both = command line, interactive programs and batch jobs; Interactive = at a terminal only (in COMMANDS.md terms I; in a batch job ELC0105).
  • Auth: the Firewall permission checked before running (ELC0401): view, insert, extract, craft, configure (the Firewall's build). A dash means none.
  • Status says how it runs:
Available runs on the command line and in programs Opens a screen opens its screen on the desk Program only a language statement, run by the VM Needs a device works, but the device it needs isn't in the mod yet (ELC1301 until it is)

Every command can also raise the general errors ELC0101–ELC0106 and ELC0401, and the OS and mod commands raise ELC1302 Device *NETWORK is offline. when the job's network is gone. The Errors columns list the escape messages a command raises besides those.

Devices

Each device that takes a name keeps it stored with the device: CTLIF01 (Control Interfaces), ELDESK01 (Terminal Desks), and rack devices FIREWALL01, ROUTER01, UPS01, SWITCH01, L3SWITCH01, CMPSRV01, MEMSRV01, FABSRV01, MONSRV01, NAS01, SAN01, RACKCON01, WLC01, TAPELIB01, and the parts on cables INGRESS01 (Ingress Port), EGRESS01 (Egress Port), TAP01 (Inventory Tap), SENSOR01 (Threshold Sensor), COLLECTOR01, DEPLOYER01 (planes), P2P01 (Point-to-Point Link), TERM01 (Access Terminal), FABTERM01 (Fabrication Terminal), ENCODER01 (Schematic Encoder), and wireless AP01 (Access Point), WBRIDGE01 (Wireless Bridge), WINGRESS01 / WEGRESS01 (Wireless Ingress / Egress Ports: ELCL treats them exactly as the cabled ports). A name is given once, the first time the device is on a network: its type and the lowest number free there. It never changes after that unless someone renames it (RNMDEV DEV(UPS02) NEWNAME(MAINUPS), or Work with Devices 2=Change; Firewall build permission): ELC1309 Device &1 renamed to &2. Names are unique on a system: a rename to a name in use is ELC1308 Device name &1 is already used on &2., and a name that isn't a valid name (up to 10 characters: a letter, then letters, digits, _, @, # or $) is ELC0103. Adding or removing a device never renames another; a removed device's name is free again. A rack device carries its name on its item, and a Terminal Desk or Control Interface on its block item (a cable part keeps its name while it is on its cable), so one moved to another network keeps its name there if it is free, and otherwise gets the next free number (the system remembers which device holds each name, so the device already there keeps it). Worlds from before names were stored get, on first load, exactly the names counting gave them (rack by rack, each rack from its lowest unit up). COMMANDS.md also mentions naming with the Label Maker; the mod has no Label Maker, so renaming is through RNMDEV and Work with Devices only. The prompter's F4 list on a device parameter shows the names in use.

A device's type (RTVDEVLST TYPE(), RTVDEVSTS RTNTYPE) is its name prefix: CTLIF, DESK, the rack devices' (UPS, NAS, TAPELIB...) and the cable parts' (INGRESS, EGRESS, TAP, SENSOR, COLLECTOR, DEPLOYER, P2P, TERM, FABTERM, ENCODER). Only cable parts can be enabled and disabled (a disabled part works as if it were offline, and its status is *DISABLED), and only ports, taps and planes have filters; anything else is ELC1303.

8. Jobs, scheduling, triggers, message queues, spooled output and system values

Jobs

ELCL work runs in jobs. These are script jobs, separate from the network's crafting jobs (WRKCRFJOB).

Interactive job
One per open Terminal Desk session, started by the session's first request. Name QINTER, type INT, host the desk's device name (ELDESK01), priority 5, command logging on. Commands typed on the command line run in it, and so does a program started with CALL there (one at a time; budget 200 instructions a tick). It ends when the terminal closes (ELC0307 in its log), ending any program it is running, and its log joins the kept logs of ended jobs. Interactive jobs live only as long as their session and aren't saved.
Batch job
Submitted with SBMJOB CMD(command) JOB(name) HOST(*ANY|host) LOG(*NO|*YES), by a schedule entry or by a trigger, and run on a job host, as the user who submitted it, with that player's Firewall permissions, whether they are online or not. Its command can be any command allowed in batch; usually it is CALL PGM(...). SBMJOB answers ELC0304 Job &1 submitted to job queue on &2. and the job waits on the job queue (*JOBQ) until a host has room. Each tick, queued jobs go to an online host with a free slot (any host for HOST(*ANY), else the one named), in priority order (1 first; CHGJOB JOBPTY()) and then oldest first, while fewer than QMAXJOB batch jobs are running on the system. A system with no job host at all refuses the job straight away with ELC0301, as does a HOST() it doesn't have.

When its host goes offline (unloaded, removed or out of power) or the server restarts, a job on a host that doesn't resume ends with ELC0310 Job ended: job host &1 was unloaded or lost power., which is logged and sent to the job's user; a job on a resuming host pauses while the host is down and, after a restart, carries on where it was once the host is back. Queued and held jobs that hadn't started wait through a restart either way.
Job IDs
nnnnnn/USER/JOBNAME, for example 000123/ZAGDRATH/RESTOCK. Commands accept the number, the full ID, or the job name alone if only one job that hasn't ended has it (ELC0302 otherwise). Numbers start at 000001 on each system, are shared by interactive and batch jobs, are saved, and wrap round after 999999.
Statuses
*JOBQ (waiting for a host), *ACTIVE, *WAIT (in a DLYJOB, a tape recall or a craft wait), *HELD, *MSGW (defined, not used: no message needs a reply), *ENDED (an ended job whose log is kept).
Holding, releasing, ending
HLDJOB holds a queued job (it won't start) or pauses a running one where it is; RLSJOB lets it go on (back to *JOBQ if it hadn't started). ENDJOB takes a queued job off the queue or stops a running program before its next instruction, with either *CNTRLD or *IMMED; the batch job then ends with ELC0303 Job ended by operator. in its log and in its user's messages. Managing another user's job takes *SECOFR (ELC0401 naming *JOBCTL).
Unmonitored errors
A program ended by an escape message it didn't monitor puts that message in the job log and in the job user's message queue (MW), then the job ends.
Budget
Each job's share of its per-tick instruction budget on the last tick, shown on Work with Active Jobs; see limits and runtime model.

Commands on jobs: WRKACTJOB, WRKJOB, DSPJOBLOG, CHGJOB (priority 1–9, logging), HLDJOB, RLSJOB, ENDJOB OPTION(*CNTRLD|*IMMED), SBMJOB, RTVJOBA.

Job logs

Every job keeps a log of the commands it ran (when it logs commands: always for the interactive job, LOG(*YES) on SBMJOB or CHGJOB LOG(*YES) for batch jobs) and every message it got, with ID, severity, sender and time. A batch job's log starts with ELC0304 and ends with how it ended (ELC0307, the escape message that ended it, ELC0303 or ELC0310). View it with DSPJOBLOG or WRKJOB option 10, or print it with PRTRPT RPT(*JOBLOG) from inside the job. When a job ends, its log is kept with the system's ended jobs: the last LOGRTN of them (default 50), saved with the system. Name an ended job by its number or full ID to see its log.

Job schedule entries

ADDJOBSCDE JOB(name) CMD(command) FRQ(*ONCE|*DAILY|*INTERVAL) TIME(HHMM) INTERVAL(seconds) adds an entry that submits CMD as a batch job, named after the entry, when it's due.

  • *ONCE: at the next time the game clock reaches TIME (the day starts at 06:00; *CURRENT, the default, means now). It is removed once it has run.
  • *DAILY: every day at TIME on the game clock. If its network was unloaded through one or more of its times, it runs once when the network is loaded again, not once per day missed.
  • *INTERVAL: every INTERVAL real seconds (1–604800; required with FRQ(*INTERVAL)), the first one INTERVAL seconds after it is added. Real time, so it keeps its pace whatever the game clock or the server's tick rate does. (This was HANDOFF open question 2; the code follows the proposal.)
  • Entries fire only while their network is loaded, whether or not anyone is signed on. The job runs as the user who added the entry, with their Firewall permissions. If it can't be submitted (no job host: ELC0301), the message goes to that user's message queue as "Schedule entry NAME: ...".
  • Work with Job Schedule Entries shows each entry's next run on the game clock (an *INTERVAL entry's as near as real seconds go). 10=Submit now submits it at once without changing its next run.
  • Hold and release with HLDJOBSCDE / RLSJOBSCDE (status *HLD / *SCD); a held entry doesn't fire. Remove with RMVJOBSCDE. Entries are saved with the system.

Message queues

  • Each user has a message queue, shown newest first by DSPMSG (Main Menu 7). While it holds unread messages, MW shows at the end of the message line on every screen.
  • SNDMSG MSG('text') TOUSR(...) puts a message in a queue:
    • *REQUESTER (default): your own queue.
    • a user name: that user's queue.
    • *SYSOPR: the system operator's queue, QSYSOPR. Its chat notice goes to the network's owner (the Firewall's owner), but DSPMSG always shows your own queue, so no screen shows QSYSOPR yet. (COMMANDS.md says *SYSOPR is the network owner.)
    • *ALL: every queue that already exists on the system, plus QSYSOPR.
  • Online recipients get a chat notice that a message is waiting (server config messageChatNotice, on by default). TOTRM is accepted but not used.
  • The system puts messages in queues too: a job's unmonitored escape message goes to its user's queue (sent by the program); a batch job ended by ENDJOB or a lost host (ELC0303, ELC0310) and a schedule entry or trigger that couldn't submit its job are sent by QSYS.
  • Queues are saved with the system and keep at most 500 messages each (config messageCap); past that the oldest go. No message needs a reply.

9. The Control Interface

The Control Interface is a network device block that gives ELCL redstone input and output. It has no GUI: you drive it from a terminal with RTVRSIN and CHGRSOUT.

  • Network device. It takes one lane and drains controlInterfaceDrain FE/t while its network runs (server config, default 1.0, range 0–1000). It is online while its network is.
  • Name. The first time it is on a network it takes the lowest free name of the form CTLIFnn (CTLIF01, CTLIF02...) and keeps it, on its item too when it is broken; RNMDEV renames it. It appears under that name in Work with Devices and the prompter's device list.
  • Six channels. Each face (*NORTH, *SOUTH, *EAST, *WEST, *UP, *DOWN) has its own input and output level, 0–15.
  • Reading. RTVRSIN DEV(CTLIF01) SIDE(*NORTH) RTNLVL(&L) returns the level arriving on that face; SIDE(*MAX) returns the highest of the six. A face never reads the block's own output back: while it measures it gives out nothing, and redstone dust it powers itself only counts when something else drives that dust higher.
  • Writing. CHGRSOUT DEV(CTLIF01) SIDE(*UP) LVL(15) sets what a face gives out; SIDE(*ALL) sets all six. A level outside 0–15 is ELC0004.
  • Weak power only. The output powers a component directly next to the face (a lamp, dust, a repeater), but it never strongly powers a solid block there, so it doesn't reach through that block to things beyond it.
  • Offline. While offline it gives out nothing, but it keeps its output levels (they're saved with the block) and gives them out again when it comes back online. Both commands answer ELC1302 Device CTLIFnn is offline. while it's offline, and CHGRSOUT then stores nothing.
  • Errors. A name no device has is ELC1301; a device that isn't a Control Interface is ELC1303.
  • Authority. RTVRSIN needs the Firewall's view permission, CHGRSOUT its build (configure) permission.
  • LEDs. Each face has an LED showing the higher of what comes in and what goes out there: off (0), dim (1–7) or bright (8–15). The block also shows whether it is online.
  • Events. When the level arriving on a face changes, the block fires a *RSCHANGE event once per change, with its device name and &DATA like *NORTH 7. A *RSCHANGE trigger on it (optionally for one side, VALUE(*NORTH)) runs its program then.
RTVRSIN CTLIF01 *MAX                   /* Command Entry shows RTNLVL = 9            */
CHGRSOUT CTLIF01 *ALL 15               /* every face on, full strength              */
CHGRSOUT DEV(CTLIF01) SIDE(*UP) LVL(0) /* top face off                              */

10. Status, limits and server config

The Terminal OS and ELCL are complete as specified in docs/elcl/: every screen, all 99 commands, every message, the VM, interactive and batch jobs, job hosts, schedule entries and triggers, persistence, stable device names, sign-on and security, folder sync, and SAVLIB / RSTLIB. docs/elcl/IMPLEMENTATION_STATUS.md has the details, part by part. What remains is hardware the mod doesn't have yet, and a few known limits.

Known limits

  • Source storage is counted, not reserved. Members count against free drive space (and ELC0207 stops a save that doesn't fit), but items going into the network don't check for them, so items can fill the drives past the members' share (storage cost).
  • %NAME on dedicated servers. Item names are worked out on the server, which may not have a mod's translations: %NAME of a mod's item can come back as its translation key (item.encodedlogistics.logic_die).
  • Long event names. In the *CHAR 10 &EVENT the spec gives a trigger program, *DEVOFFLINE and *PWRRESTORED arrive as *DEVOFFLIN and *PWRRESTOR.
  • Interactive jobs aren't saved. A program called from a terminal ends when its terminal closes or the server stops; use SBMJOB for anything long-running.
  • Device status after a restart. Device statuses for the *DEV... triggers aren't saved: the first look after a restart only records them, so a change while the server was down doesn't fire.
  • *SYSOPR messages go to a QSYSOPR queue no screen shows (its chat notice does reach the network's owner). SNDMSG TOTRM(), DSPMSG USR() and WRKINV FILTER() are accepted but not used.
  • SYSNAME doesn't change the screen header, and DATFMT doesn't change the header's clock (it does change the dates the system writes).
  • CHGJOB, HLDJOBSCDE, RLSJOBSCDE, HLDTRGEVT and RLSTRGEVT succeed silently, with no completion message.
  • *MSGW is defined but never used: no message asks for a reply.
  • Rendering in each phosphor at every GUI scale isn't covered by automated tests.

How a command line runs

  1. CrtTerminal.runCommand (client): clear is handled here; ScreenCommands.open opens screens for screen commands; anything else goes to the server as a COMMAND request.
  2. TerminalDeskMenu starts the session's interactive job if needed and calls TerminalService.handle.
  3. TerminalCommands.execute: ElclCommandLine.run (the screens' own requests - withdraw, craft, cancel a job - go to TerminalService, not the command line).
  4. CommandRunner.run: Parser.parseCommand, unknown command (ELC0101), context (ELC0106), Compiler.checkCommand, Firewall permission (ELC0401, through Authority), no executor (ELC0107), then the executor with an Invocation whose values are worked out from the literals. CALL's executor (InteractiveCalls) starts a VM in the interactive job and returns at once; JobManager runs it on the following ticks and sends its messages to the terminal when it ends.
  5. ElclCommandLine logs the command and messages in the interactive job and formats the output; the response carries the unread message count for MW.

Inside a program the VM does the same per command (Vm.registered): context (ELC0105 / ELC0106), authority through the run's JobVmHost (the submitter's permissions in a batch job), then the executor with an Invocation over the frame's variables. An executor that needs to wait calls call.await(Wait) when call.canWait(); the VM parks the job and runs the command again (call.resumed() set) once Waits.done says so.

The OS screens fetch their data with SCREEN requests answered by ScreenQueries (libraries, members L, source L M [from], lock/unlock, savebegin/savepart/savecommit, jobs, joblog J, callstack J, schedules, triggers, messages, spooled, splf N, printsplf N, sysvals, signon USER [CURLIB], values KIND [filter] and so on). These need the Firewall's view permission; until a session has signed on (where it must), only info and signon are answered.

How to add a command

  1. Register the schema once, during setup: 
    CommandRegistry.register(CommandDefinition.of("RTVFOO", "Retrieve Foo")
        .auth(CommandDefinition.Auth.VIEW)         // Firewall permission (default NONE)
        .positional(1)                             // first N params may omit keywords
        .p(ParamDef.of("DEV", "Device", ParamDef.Kind.DEVICE).req())
        .p(ParamDef.of("MODE", "Mode", ParamDef.Kind.SPECIAL).sv("*FAST", "*SLOW").dft("*FAST"))
        .p(ParamDef.of("RTNVAL", "Return value", ParamDef.Kind.VARIABLE).returns(ParamDef.VarType.INT))
        .build());
    Context defaults to BOTH; use .context(Context.INTERACTIVE) or PROGRAM as needed. Other builder calls: .list(n), .range(min, max), .len(n) (prompter field), .values(ValueList.X) (F4 list). Registering a name twice throws. Built-ins go in BuiltinCommands.register(); other devices register from their own setup.
  2. Bind the executor (built-ins in ElclSetup.init via OsCommands.bind / RedstoneCommands.bind): 
    CommandRegistry.bind("RTVFOO", call -> {
    ElclContext context = call.context(ElclContext.class);   // server, network, user, allowed()
    String dev = call.text("DEV");                           // names and specials upper-cased
    if (notFound) throw new ElclException("ELC1301", dev);   // escape message
    call.returns("RTNVAL", 42);                              // RTN* value
    call.send(ElclMessage.of("ELC0222", "FOO"));             // info / completion message
});
    call.integer() raises ELC0003 / ELC0004 itself; call.given() tells a given value from a default; call.list() returns every value of a list parameter; call.interactive() says whether it runs at a terminal; call.canWait() / call.await() / call.resumed() make it async in a program.
  3. That's all for the language side. The parser, compiler checks, F4 prompter, F1 help, the command line and the VM all read the definition, and the same executor runs on the command line, in interactive programs and in batch jobs. A command with no executor answers ELC0107.
  4. New messages go in ElclMessages (and MESSAGES.md); a completion message should be added to ElclCommandLine.COMPLETION so it's shown bright.
  5. Parameters required only together (like CHGDEVFTR ITEM unless *CLR) are checked in the switch in Compiler's statement check.
  6. A device scripts talk to: give it a name (ElclDevices: a type code, and storage on the device), and if it is a printer, diskette drive, display or job host, implement the interface in elcl.device / elcl.job and register a source at setup (docs/elcl/INTERFACES.md).
  7. A command that opens a screen: add it to ScreenCommands.panel(), write a CrtPanel (or OsListPanel) subclass, add crt.encodedlogistics.* lang keys (title, F-keys, help.<id> and help.<id>.<field>), and a layout under src/test/resources/layouts/ for LayoutTest.

12. Where the spec and the code differ

This page follows the code. These are the places where it differs from docs/elcl/ (spec, COMMANDS.md, MESSAGES.md, OS.md), or where the code goes further than they say:

  1. Added messages: ELC0107–ELC0110 and ELC1307–ELC1311 came with the implementation; MESSAGES.md lists them, marked added.
  2. Extra commands: CHGLIB, CRTMBR, CHGJOB, HLDJOBSCDE, RLSJOBSCDE, HLDTRGEVT, RLSTRGEVT, WRKCRFJOB, GO, CLEAR are registered but not in COMMANDS.md; WRKSPLF isn't in its table either. RNMDEV is in COMMANDS.md, marked [EXT].
  3. Extra parameters: CRTLIB TYPE(*PROD|*TEST), SBMJOB LOG(*NO|*YES), RTVITMCNT NOTFND(*ERROR|*ZERO), WRKINV FILTER(), WRKSPLF JOB().
  4. Defaults COMMANDS.md doesn't state: MOVITM PARTIAL(*YES), PRTRPT SPLF(*LAST), SNDMSG TOTRM(*NONE), LEAVE/ITERATE CMDLBL(*CURRENT), ADDJOBSCDE TIME(*CURRENT), ADDTRGEVT ITEM(*ANY) DEV(*ANY) VALUE(*NONE), SBMJOB JOB(*JOBD) (job name QDFTJOBD).
  5. Where commands run: COMMANDS.md marks CHGVAR, MONMSG, RCVMSG and the control-flow statements IB; in the code they are program-only (ELC0106 on the command line). SNDPGMMSG runs on the command line.
  6. ENDSUBR RTNVAL: the spec shows ENDSUBR [RTNVAL(&I)]; the code takes an integer value there (default 0), and CALLSUBR RTNVAL is the *INT variable that receives it.
  7. Operators: the code also accepts *NG, *NL and ¬=. ¬ can't be typed on the terminal (ASCII only).
  8. Continuation with -: outside strings, the code treats a trailing - exactly like +; inside strings, - drops the next line's leading blanks as the spec says.
  9. System values: OS.md doesn't list allowed values; the code allows DATFMT *DAY *MDY *DMY *YMD (a calendar of 30-day months), SYSNAME 1–8 letters and digits, QMAXJOB 1–999, LOGRTN 0–999. SYSNAME isn't shown in the screen header (the network name is), and the header's clock always shows "Day n".
  10. *SECOFR: OS.md says the network owner; the code takes the Firewall's owner and server operators. Without a Firewall everyone has full authority, so anyone may change system values there.
  11. SNDMSG TOUSR(*SYSOPR): COMMANDS.md says the network owner; the code uses a QSYSOPR queue (its chat notice goes to the owner), which no screen shows. *ALL reaches only queues that already exist, plus QSYSOPR.
  12. Missing "not found" IDs: removing, holding or releasing an unknown trigger is ELC0103 (value not valid for TRG), and an unknown schedule entry is ELC0302 (job not found).
  13. Silent commands: amendment 2 says every successful OS command returns its completion message, but CHGJOB, HLDJOBSCDE, RLSJOBSCDE, HLDTRGEVT and RLSTRGEVT have no message defined and send none; SNDMSG, PRTTXT, CHGDEVSTS and CHGDEVFTR send none either.
  14. Device names: COMMANDS.md mentions naming with the Label Maker; the mod has no Label Maker. Names are given to Control Interfaces, Terminal Desks, rack devices and the parts on cables.
  15. Item tiers: the mod has no per-item tier, so CHGITMTIER works through the Tape Libraries' keep-hot, pin and archive lists.
  16. Trigger &EVENT: the spec's *CHAR 10 can't hold *DEVOFFLINE or *PWRRESTORED; they arrive cut to 10 characters.
  17. DLYJOB seconds are game seconds (20 ticks), and DLYJOB on a command line completes at once.
  18. Editor F19/F20 shift 8 columns (1–72 and 9–80); the screens handoff said 40. Display Spooled File does shift 40.
  19. Sign On appears only when the network has a Firewall (and SECLVL is 30); without one there is nothing to sign on to, as everyone has full authority.
